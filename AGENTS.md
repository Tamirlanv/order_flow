# Правила разработки OrderFlow

## Обязательный контекст

Перед любой работой прочитать:

1. [Требования](docs/REQUIREMENTS.md).
2. [Архитектуру](docs/ARCHITECTURE.md).
3. [Актуальный план и точку остановки](docs/PLAN.md).
4. Спецификацию затрагиваемой функции из [docs/features](docs/features/README.md).

Инструкции пользователя имеют приоритет. Если меняется согласованное продуктовое поведение, сначала обновить спецификацию. При существенной неоднозначности спросить пользователя; рутинные технические решения принимать самостоятельно и кратко фиксировать их обоснование.

## Текущая граница работ

С 2026-10-13 пользователь разрешил реализацию по плану, отдельные feature-ветки, коммиты, merge и push в настроенный `origin` (`https://github.com/Tamirlanv/order_flow.git`). Каждую функцию разрабатывать в `feature/<этап>-<имя>`, после проверок сливать в `main` через `--no-ff` и отправлять обе ветки без force-push. Если этап имеет отложенные проверки, сливать только явно выделенную и проверенную часть; не отмечать весь этап завершённым.

Запрет на запуск контейнеров и развёртывание сохраняется. Наличие файлов Docker не означает разрешения на их запуск. CI выполняет проверки исходников без запуска контейнеров, публикации образов и deploy. Пользовательские незакоммиченные файлы не изменять и не включать автоматически в коммиты. README обновлять по фактическому состоянию проекта, используя структуру пользовательского `docs/README_example.md` как ориентир, без чужих достижений, брендов и несуществующих ссылок.

## Рабочий цикл

1. Перед работой прочитать требования, архитектуру и актуальный план; проверить `git status`.
2. Реализовывать по одной законченной функции за раз, последовательно по плану.
3. Для существенной функции сначала описать поведение, ошибки, границы и проверяемые критерии приёмки в `docs/features/`. Указать связь с требованиями и этапом плана.
4. Проверять новое поведение подходящими тестами: unit для правил, интеграционные для БД/API/воркеров, сквозные для ключевых пользовательских сценариев. Не подменять проверку поведения тестом деталей реализации.
5. Запускать доступные проверки проекта и исправлять ошибки своих изменений. Не обходить запрет на контейнеры; недоступные интеграционные проверки обозначать как незапущенные. Пока нет разрешения на инфраструктуру, такие этапы не считать полностью проверенными.
6. Просматривать изменения перед коммитом: `git diff`, после staging — `git diff --cached` и `git diff --cached --check`.
7. Обновлять документацию и состояние плана вместе с кодом. Команды README должны соответствовать существующим файлам и возможностям.
8. После законченного проверенного этапа делать локальный Git-коммит. Добавлять файлы явно. Не включать посторонние изменения, секреты, логи, артефакты сборки и локальные данные. Не переписывать историю без указания пользователя.
9. Не выдавать незапущенные проверки за успешные. В плане фиксировать точные команды, результат и ограничения. Статическая проверка Compose не равна запуску системы.
10. При остановке сохранять в плане текущий статус, препятствия и следующий шаг. Если проверка не прошла, этап остаётся незавершённым; допустимый промежуточный коммит явно маркировать как незавершённую работу.

## Инженерные правила

- Backend — модульный монолит; отдельные процессы API, Celery worker и единственный scheduler. Новые микросервисы вводить только при обоснованной необходимости.
- Все операции над данными магазина проверяют членство и роль. Переданный клиентом `store_id` не является доказательством доступа. Кэш, файлы и фоновые задачи тоже изолированы по магазинам.
- Источник истины для заказов и остатков — PostgreSQL. Денежные значения — decimal/NUMERIC, не float; валюта MVP — KZT.
- Изменения схемы — миграциями Alembic. Не использовать SQLite как доказательство корректности блокировок PostgreSQL.
- Внешние вызовы не выполнять под длительной транзакцией/блокировкой БД. Настраивать таймауты, ограниченные повторы и идемпотентность.
- Не обещать доставку exactly-once. Дубли сообщений ожидаемы; бизнес-эффект должен быть защищён от повторного применения.
- Не писать токены, пароли, ключи API, персональные данные и полные webhook payload в логи.
- Покрывать правами и тестами чтение чужих данных, конкурентный резерв, дубли событий, истечение и повторное использование ссылок восстановления.
- До реализации фиксировать зависимости и добавлять команды проверок в README. Не добавлять инструменты только ради списка технологий.
- Не делегировать работу другим агентам без просьбы пользователя.

## Завершение этапа

Готовность: выполнены критерии функции, выполнены доступные обязательные проверки, просмотрен diff, обновлены документы, создан локальный коммит. Если обязательная проверка недоступна, указать причину и оставить соответствующий пункт приёмки открытым.
