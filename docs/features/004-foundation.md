# M01 — запускаемая основа приложения

Статус: M01a реализован и локально проверен; M01b отложен. Основание: M01 в [плане](../PLAN.md), разрешение пользователя от 2026-10-13.

## Цель и границы

Подготовить проверяемую основу для следующих функций: FastAPI, веб-интерфейс React, конфигурацию, SQLAlchemy/Alembic и Celery. Бизнес-функции заказов и аккаунтов не реализуются в этом этапе. Рабочая ветка: `feature/m01-foundation`.

M01 делится на M01a (исходники и проверки без инфраструктуры) и M01b (реальный PostgreSQL, broker и сборка/запуск образов). M01a может быть принят отдельно; M01 целиком не считается завершённым до M01b. Запуск контейнеров не разрешён; не заменять тесты PostgreSQL тестами SQLite.

## Поведение и API

- `GET /health/live` и `GET /api/v1/health/live` возвращают 200 `{"status":"ok"}` без обращения к инфраструктуре.
- `GET /health/ready` и API-alias проверяют PostgreSQL, Redis и RabbitMQ с ограниченным временем ожидания. Ответ 200 только при доступности всех зависимостей; иначе 503. В ответах только статусы компонентов, без исключений/строк подключения.
- `GET /api/v1/system` возвращает название, версию и стадию разработки для стартовой страницы. Секреты, пути и адреса инфраструктуры не возвращаются.
- `/docs` и `/openapi.json` описывают доступный API.
- Страница приложения открывается без БД. Показывает назначение OrderFlow, готовность API и доступные проверки; запланированные функции явно обозначены. Ошибка API не превращается в пустой экран; кнопка повторной проверки работает.
- Конфигурация читается из окружения и корневого `.env`. Development имеет только локальные демонстрационные значения; production требует заменённых секретов и HTTPS origin.
- Celery и SQLAlchemy создаются без сетевых соединений при импорте. Воркеры и Beat не запускаются тестами/импортом. Отсутствие брокера не мешает `/health/live`.

## Данные и миграции

Добавляется пустая базовая ревизия Alembic для воспроизводимой истории; бизнес-таблицы появятся вместе с функциями. Генерация offline SQL проверяет конфигурацию/цепочку ревизий, но не является выполнением миграции на PostgreSQL.

## Приёмка M01a

1. API стартует локально без Docker; liveness и system доступны, readiness показывает недоступность отсутствующей инфраструктуры.
2. Тесты проверяют healthy/unhealthy/timeout readiness, отсутствие секретов в ответах, конфигурацию и lifecycle ресурсов. Сетевые проверки подменяются на границе адаптера и не выдаются за интеграционные.
3. В frontend есть состояния загрузки, успешного подключения и ошибки, а также повтор запроса; типы API проверены во время выполнения.
4. Ruff, mypy, pytest, TypeScript, ESLint, frontend tests и production build выполняются локально.
5. Зафиксированы прямые и транзитивные Python/npm зависимости; Dockerfile использует существующие файлы, Compose проходит статическую проверку.
6. CI запускает те же проверки без контейнеров, секретов, публикации и deploy.
7. README содержит собственный баннер, навигацию, реальный статус, архитектуру, команды запуска/проверок и ограничения.

## Отложенная приёмка M01b

Реальные upgrade/downgrade Alembic на чистой PostgreSQL, readiness со всеми сервисами, подключение worker к RabbitMQ, Docker build/run и smoke test полного окружения. До отдельного разрешения контейнеров или предоставления разрешённого внешнего тестового окружения эти проверки не запускать и не считать пройденными.

- 2026-10-13: `./scripts/check.ps1` — успешно: pip check, Ruff check/format, mypy, первоначальные 9 pytest-тестов, offline Alembic SQL, ESLint, Prettier, TypeScript, 5 Vitest-тестов, frontend production build, статическая проверка Compose и git diff check. После review добавлена защита вывода секретов в ошибках настроек: повтор Ruff/mypy/pytest успешен, итог **11 backend-тестов**.
- Импорт Celery entrypoint и `alembic heads` — успешно, без запуска воркера/миграций на сервере.
- HTTP smoke локального процесса: live 200, system 200, OpenAPI 200, readiness 503 с тремя unavailable зависимостями. Это ожидаемый результат при выключенной инфраструктуре.
- Браузер: API подключён, переход обзор/план и повтор запроса работают, ошибок console нет. Это ручная smoke-проверка, не E2E бизнес-процессов.
- `npm audit` после обновления Vitest и ESLint — 0 обнаруженных уязвимостей на дату проверки.
- Ни контейнеры, ни PostgreSQL/Redis/RabbitMQ не запускались. M01b не проверен; бизнес-API пока отсутствует.
