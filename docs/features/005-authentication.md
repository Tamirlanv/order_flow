# M02a — аккаунты и сессии

Статус: реализовано; локальные проверки и GitHub Actions пройдены. Связь: M02a, сценарий 1, AC-18, требования безопасности. Ветка `feature/m02-authentication`.

## Поведение

Посетитель регистрируется по email и паролю, получает письмо в Mailpit и подтверждает адрес. После подтверждения он входит в кабинет. Создание магазина — отдельный M02b. Пароль: 12–128 символов, Unicode и пробелы разрешены; Argon2id, без произвольных требований к набору символов. Email валидируется и нормализуется (trim + lower).

Регистрация отвечает 202 одинаковым сообщением для нового и существующего email; существующий пароль не меняется. Для нового аккаунта сохраняются User и одноразовый EmailVerification. Повторная отправка доступна отдельным запросом с нейтральным ответом. Подтверждение действует 24 часа; повторный запрос аннулирует прежний токен. Токен — 32 случайных байта, в БД только SHA-256. Ссылка строится из PUBLIC_APP_URL с fragment `#verify=...`; GET не расходует токен. Пользователь явно нажимает «Подтвердить email».

До M04c письмо отправляется SMTP-адаптером после commit с ограничением времени 5 секунд, вне транзакции БД. Статус `pending/sent/failed` хранится на записи подтверждения. Raw токен передаётся только в памяти адаптеру. При сбое публичный ответ остаётся нейтральным; UI объясняет возможность повторной отправки. После M04c — шифрованный outbox и worker (не выдавать текущую отправку за гарантированную).

Вход разрешён только с подтверждённым email. Ошибка пароля/неизвестный email дают одинаковый 401; правильный пароль при неподтверждённом email — 403 с предложением повторить письмо. Сессия: 32 случайных байта, SHA-256 в PostgreSQL, TTL 7 суток без автоматического продления. Новый вход не отзывает другие сессии, но заменяет сессию текущего браузера. Выход отзывает текущую сессию; истёкшая/отозванная сессия больше не авторизует запросы.

## Контракт

| Endpoint | Результат |
| --- | --- |
| GET `/api/v1/auth/csrf` | Токен для X-CSRF-Token, no-store |
| POST `/api/v1/auth/register` | email/password → 202, нейтральное сообщение |
| POST `/api/v1/auth/verification/request` | email → 202, нейтральное сообщение |
| POST `/api/v1/auth/verification/confirm` | token → 204; неизвестный/истёкший/использованный → общий 400 |
| POST `/api/v1/auth/login` | email/password → user + CSRF token, сессионная cookie |
| GET `/api/v1/auth/me` | Текущий user; 401 без действующей сессии |
| POST `/api/v1/auth/logout` | Отзыв текущей сессии, удаление cookie, 204 |

Все изменяющие browser-запросы проверяют точное совпадение Origin с настроенным origin и X-CSRF-Token. CSRF — HMAC от случайного HttpOnly anonymous seed либо raw сессии; после входа привязка меняется на новую сессию. Cookie host-only, Path=/, HttpOnly, SameSite=Lax; Secure при HTTPS. Ответы auth — no-store; 422 не содержит исходный пароль/токен. Пароли, email, raw ссылки не логируются. Клиент не задаёт verified/roles/user_id.

Redis атомарно ограничивает регистрацию/повтор письма: 10 запросов в час на IP, 3 письма в час на нормализованный email (превышение email скрыто тем же 202). Вход: 20 запросов за 15 минут на IP и 10 на email. Подтверждение: 20 в минуту на IP. Ключи содержат HMAC, не исходные email/IP. Сбой Redis → общий 503; IP/login лимит → 429 с Retry-After. Блокировки БД не удерживаются во время SMTP/Argon2.

## Проверяемая приёмка

1. Регистрация → SMTP → одноразовое подтверждение → вход → me → выход → 401 работает с PostgreSQL, Redis и Mailpit.
2. До подтверждения вход запрещён; повтор/истечение/случайный токен отклонены, две конкурентные попытки дают ровно один успех.
3. Повторная регистрация не меняет пароль; повтор письма аннулирует прежний токен. Конкурентная регистрация не создаёт два аккаунта.
4. Неверный пароль и неизвестный email дают одинаковый 401; истёкшая и отозванная сессии дают 401.
5. Изменяющий запрос без CSRF или с чужим Origin отклоняется; токен старой сессии не подходит к новой. Флаги cookie и скрытие секретов в 422 проверены.
6. Проверены лимиты и отказ при недоступном Redis; SMTP failure оставляет `failed`, повторная отправка восстанавливает сценарий.
7. Frontend показывает регистрацию, вход, подтверждение, повтор письма, состояние текущего пользователя и выход; ошибки доступны читателю экрана, пароли не сохраняются в storage.
8. Миграции upgrade/downgrade пройдены на временной PostgreSQL; unit, PostgreSQL/API, UI tests, сборки и доступный CI проходят.

## Проверки

Unit: пароли/хэши, CSRF, часы, SMTP failure. Интеграции: реальные ограничения БД, одноразовость и конкуренция, сессии, Redis, Mailpit. Браузер: успешный сценарий на Compose. Часы инъецируются; время не ждём в реальности. Бизнес-роли/магазины/восстановление пароля — M02b/M02c.
