# Магазины, роли и изоляция

Статус: проект, реализация не начата. Этап M02b. Требования AC-01, AC-02, AC-18.

## Поведение

Подтверждённый пользователь создаёт магазин и становится owner. Одна транзакция создаёт Store и Membership. Пользователь выбирает активный магазин в интерфейсе, но сервер проверяет членство на каждом запросе независимо от состояния UI.

Owner приглашает manager/warehouse по email. Приглашение ограничено магазином, адресом и ролью, действует 24 часа и используется один раз. Его принимает аккаунт с подтверждённым совпадающим email. Изменение роли в теле запроса принятия запрещено. Новый владелец и передача владения вне MVP.

## API и данные

Целевой префикс `/api/v1`. `POST /stores`, `GET /stores`, `POST /stores/{store_id}/invitations`, `POST /invitations/accept`. Списки возвращают только доступные магазины; чтение сущности требует membership и совпадения store_id.

Ключ API ограничен магазином, scopes `orders:read`/`orders:write`, может быть отозван владельцем. Получить полный ключ повторно нельзя. История действий сохраняет автора; удаление членства немедленно прекращает доступ независимо от активной сессии.

## Приёмка и тесты

- Создание магазина даёт единственного владельца и не оставляет частичных записей при ошибке.
- Один пользователь может иметь разные роли в A и B; права не переносятся между магазинами.
- Запросы участника A к заказу, задаче, файлу B возвращают 404 без раскрытия данных.
- Warehouse не может изменять цены, роли, ключи и запрашивать отчёты; API возвращает 403.
- Повторное, истёкшее или адресованное другому email приглашение не создаёт членство.
- Отозванный ключ не создаёт и не читает заказы; scopes проверяются отдельно.
- Интеграционные тесты проверяют прямые API-запросы и межмагазинные внешние ключи БД, а не только интерфейс.

Фактические проверки: отсутствуют; это спецификация.
